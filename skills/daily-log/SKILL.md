# 今日日志

## 这个 skill 做什么

用户会同时在很多个 agent / 上下文里干活，晚上再回忆很困难。本 skill 的做法是：**在每个上下文结束时，趁信息最完整，由当前 agent 写一条记录，追加进当天唯一的日志文件**。一天下来，日志文件就是拼好的，不需要再重建。

**取材范围默认是"当前上下文里今天做的部分"**，不是整个上下文。一个上下文可能跨了好几天，前面的内容早就在各自的日期里记过了，重复写入会把日志写乱。只有用户明确说"把整个上下文都记下来""从头到尾都写"，才覆盖全部上下文，并按实际发生日期分别归档（早于今天的部分在标题后加"（补录）"）。

这份日志的读者是**半年后的用户本人**：他要用它来复盘、写简历、写博客、丰富个人经历。所以写的时候始终问自己一句：**半年后他想讲这段经历，这条记录能给他什么素材？**

## 配置（只改这里）

- 日志目录：`~/daily/`（当前用户主目录下的 `daily`；Linux/macOS 为 `/home/<用户>/daily/`，Windows 为 `C:\Users\<用户>\daily\`）
- 文件名：`YYYY-MM-DD.md`（例：`2026-09-20.md`）
- 日界线：凌晨 4:00 之前算前一天

所有 agent 必须指向同一个目录。如果当前 agent 写不进这个目录（沙箱、权限），不要悄悄写到别处：把条目按下面的格式直接输出给用户，并说明没能写入，由用户自行粘贴。

## 工作流程

1. **取时间**：用系统时钟，不要凭感觉猜日期。GNU 系统用 `date -d '4 hours ago' '+%Y-%m-%d'` 得到"今天"的日期，macOS 用 `date -v-4H '+%Y-%m-%d'`；条目时间用 `date '+%H:%M'`。原因是不同 agent 对"今天"的认知不可靠，日期错了整套归档就乱了。
2. **读已有文件**：文件存在就先读一遍，看清已有条目的格式、长度、项目标签写法，照着对齐。这样即使换了不同的 agent 或模型，同一天的日志读起来也像出自一人之手。
3. **判断值不值得记**：上下文里没有实质产出（几句闲聊、一次性查询）时，告诉用户"这段没什么值得记的"，不写入；用户坚持再写。
4. **回顾上下文取材**：先划出取材范围——**默认只看当前上下文里属于今天的那部分**。跨天的上下文里，早先几天的内容通常已经在各自的日期里记过，重复记会让日志出现两份同样的事。只有用户明确要求"整个上下文都记"，才从头回顾。

   范围定好后不要从头到尾复述，重点扫这几类位置：方向改变的地方、报错和卡住的地方、做了选择的地方（选了什么、放弃了什么）、最终验证过的结果，以及用户当场纠正过自己的地方。
5. **写入**：
   - 文件不存在：先建文件，开头写 `# YYYY-MM-DD 周X`，再空一行写 `## 概览` 与 `（待收口）`，然后追加条目。
   - 文件存在：用**追加写入**加到末尾。不要把整个文件读出来再覆盖写回，因为多个 agent 可能同时在写，覆盖会吞掉别人的条目。
   - **同一上下文重复调用**：找到本上下文此前写的那一条（按标题定位），只重写这一条，不新增。改写前重新读一次文件，确保拿到最新内容。
   - 补录（记一个早已结束的上下文，或用户要求记录整个上下文里早于今天的部分）：正常写，标题里在主题后加"（补录）"，并按实际发生日期归档到对应日期的文件里。
6. **回显**：写完后只回复文件路径和刚写入的条目，不加额外评论。

## 条目格式

固定使用下面的结构，标题名称和顺序不要改动。"巧思"和"遗留"没有内容时**整段省略**，不要写"无"。

```
## HH:MM · 主题短语  #项目标签 #类型标签

> 来源：<agent 名称> · <工作目录或项目名>

**一句话**：做了什么、解决了什么、结果如何。

**做了什么**：目标和起因；过程中在哪些岔路口选了什么、放弃了什么、为什么。

**问题与解决**：
- 现象 → 原因 → 解决

**巧思**：（可省）

**遗留**：（可省）没做完的、没验证的。
```

标签规则：类型标签只能从这个词表里选 1–2 个：`排障` `设计` `调研` `写作` `学习` `搭建` `复盘` `其他`。项目标签先看今天和近几天日志里已有的写法并复用，没有再新建，避免同一个项目出现三种写法，以后检索会乱。

## 内容原则

**记"为什么"，不记"怎么敲的"。** 决策理由、放弃的方案、权衡，半年后最有价值；操作步骤半年后没有价值，而且过时得快。

**问题按"现象 → 原因 → 解决"三段写。** 三段缺一不可：只有现象和解决、没有原因，读的人学不到东西。还没查出原因的，如实写"原因未查明"。

**不写代码。** 不放代码块、命令、配置片段，用自然语言描述行为和思路。工具名、模块名等专有名词可以保留，报错信息只转述含义。原因是这份日志要读的是故事，不是代码。

**巧思设门槛。** 只有当上下文里真出现了非显然的想法，比如换了个角度看问题、绕开了一个坑、一个巧妙的取舍，才写"巧思"。判断标准：用户会不会把它当作一个小技巧讲给同事听。没有就省略，不要为了显得有料而硬凑。

**区分验证状态。** 明确写出哪些已验证、哪些未验证、哪些尝试后失败。不同 agent 都有倾向把一切写成"成功了"，而日志是用户回看事实的依据，虚假的成功比空白更糟。

**不编造。** 用户没说过、上下文里没出现过的数字（耗时、提升幅度、影响范围）一律不写。没有依据就不写。

**"一句话"要成为素材。** 这一行要能单独拿出来当周报或简历要点的原料：事实型、单句、包含动作和结果，不加评价。

**隐私。** 密钥、令牌、密码、别人的私人信息不进日志；确实相关时写成"（凭据已省略）"。

## 语气与篇幅

- 中文，过去时，陈述句。以用户本人的口吻记录，主语可省略或用"我"；agent 不作为叙述主体出现，不写"本次对话中，我们讨论了……"。
- 每个小节 1–3 句；整条 200–400 字为宜，最多 500 字。用字数约束，比"简洁一点"更能让不同模型收敛到同一个长度。
- 不用 emoji，不滥用加粗（只有格式里规定的小节标题加粗）。
- 禁用：夸饰词（显著、完美、大幅、极大）、总结腔（综上所述、总的来说）、没被要求的"下一步建议"。用户没说要做的事，不写进"遗留"。

## 好与坏的对照

好的条目：

```
## 15:40 · 定时任务偶发重复执行  #订单服务 #排障

> 来源：Claude Code · order-service

**一句话**：查清了对账定时任务偶发重复执行的原因（发布期间新旧实例同时在跑），并加了互斥保护；已在测试环境验证，线上尚未观察。

**做了什么**：起因是对账数据每隔几周出现重复行。最初怀疑任务被重试，翻日志后发现重复总在发布当天，转而怀疑实例交替期间调度重叠。考虑过把调度拆到独立服务，改动面太大，放弃了。

**问题与解决**：
- 重复执行只在发布当天出现 → 发布时旧实例未停、新实例已起，两边都触发了调度 → 给任务加了执行前先抢占标记的互斥，抢不到的实例直接跳过。

**巧思**：没有去追"为什么会重叠"，而是接受重叠必然发生，把问题改成"重叠时只允许一个赢"。

**遗留**：线上还没经历一次完整发布，效果未验证。
```

坏的写法（常见毛病）：

```
今天成功排查并解决了定时任务重复执行的问题，显著提升了系统稳定性。首先我们分析了日志，然后使用了分布式锁（代码如下……）。综上所述，问题已圆满解决。下一步建议增加监控告警。
```

毛病：夸饰词、没有说原因、含代码、总结腔、擅自添加下一步、没有验证状态、没有决策和取舍。

## 收口模式

当用户说"收口今天日志""总结今天日志"，读整份文件，把 `## 概览` 下的"（待收口）"替换成 3–5 行概览，不超过 200 字，只写**单个条目里看不到的东西**：

- 今天的主线是什么，哪些条目其实是同一件事的不同侧面。
- 同一个问题或想法在多个上下文里反复出现的地方。
- 一个决定如何影响了后面的几件事。
- 汇总所有条目里未解决的遗留。

不改动任何已有条目。已经收过口的，重新收口时直接覆盖概览。
